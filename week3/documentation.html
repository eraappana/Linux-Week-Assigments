1. Introduction

I created a server status report for my Ubuntu virtual machine in CSC cPouta. I used PuTTY to connect to the server. A Bash script collects the information and generates an HTML page served by Nginx.

2. How the script works

The script stores Linux command output in variables using command substitution. It collects the generation time, uptime, root disk usage, total RAM and available RAM.

My disk_status function uses an if statement. It returns WARNING when disk usage is 80% or higher and OK below 80%.

The command df -P / sends its output through a pipe to awk, which selects the usage percentage. The script creates a temporary HTML file and then replaces index.html with the completed report.

Commands I used

  • date '+%Y-%m-%d %H:%M:%S %Z (%z)' displays the date, time and time zone. I set the server time zone to Europe/Helsinki.
  • uptime -p displays how long the server has been running.
  • df -P / | awk 'NR == 2 {print $5}' uses piping to extract the root filesystem usage percentage from the second row of df output.
  • free -m displays memory information in MiB. The script uses awk to select total and available RAM.

3. Scheduling

I used a systemd service and timer. The service runs report.sh as the ubuntu user. The timer runs the service every minute using OnCalendar=*-*-* *:*:00.

I enabled the timer with systemctl enable --now so that it starts automatically after a reboot. Persistent=true allows a missed scheduled run to be triggered when the timer becomes active again.

4. Syntax check and manual execution

I checked the script using bash -n report.sh. The syntax check passed. I then ran ./report.sh manually. It generated index.html, and the report opened successfully in my browser.

I checked the systemd service logs. Two consecutive automatic reports were generated on 15 November 2026 at 13:50:00 and 13:51:00 EET (+0200). The logs showed successful updates every minute. The timer was enabled to start after reboot.

7. Reboot test

I rebooted the virtual machine on 15 November 2026. After reboot, the report was generated at 13:59:12 EET (+0200). Automatic updates continued at 14:00:00, 14:01:00, 14:02:00 and 14:03:00.

Both the Week 2 application and the Week 3 report returned HTTP 200 OK and opened in my browser after reboot. The report schedule continued without manually restarting the timer.
